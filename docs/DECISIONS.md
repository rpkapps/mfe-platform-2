# Design decisions

Short records of the decisions that shape the platform, with the evidence behind them. Newer entries at the bottom.

## 1. Module Federation 2 through `@module-federation/vite`, hidden behind the platform

Verified in a spike (Vite 8.3, `@module-federation/vite` 1.21, `@module-federation/runtime` 2.9): a host created with `createInstance` loads `remoteEntry.js` served by `vite dev` and by `vite preview`; remote CSS is injected by the remote's own Vite client in dev and attached to the exposed module in production. The `@module-federation/dts-plugin` needs a `tsconfig.json` in every project and is disabled (`dts: false`): remotes never import each other, so cross-remote types have no consumer. MFE code never sees any of this; `@platform/vite` writes the federation configuration and `@platform/host` calls the runtime. Manifest, mount and registration contracts stay loader-neutral (`RemoteLoader` in core).

## 2. Version groups through share scopes, never singletons

React-bound packages are shared inside a share scope named after the React major (`react18`, `react19`); framework-neutral packages share in `default`. A React 18 request can only ever match a React 18 provider, so React 19 never satisfies it; two React 18 remotes share one instance (loaded-first). Without a compatible provider the remote's bundled copy is used and reported. `singleton: true` is refused for React packages by the lint rules because singletons are what breaks coexistence.

## 3. One React refresh runtime per remote development server

With plugin-react 6 the federation plugin's refresh proxy does not activate, so each remote's `/@react-refresh` is its own runtime. A remote loaded by another origin only hot-updates if that runtime was injected into the DevTools hook before the remote's React evaluated. `@platform/vite` therefore serves `/@platform/refresh-preamble`, the dev manifest advertises it, and `@platform/host` imports it before loading a dev remote. Verified: editing a React 19 and a React 18 remote hot-updates both while shell and remote state survive; production artefacts have no `dev` block and are never presented as HMR-capable.

## 4. Overlays through React Aria's portal context, not the DOM

`@tecton/react/tecton/portal` (added to the Tecton repository for this platform) wraps `UNSAFE_PortalProvider` from `react-aria`. Every MFE root gets a body-level overlay root tagged with its `data-mfe`, so dialogs escape MFE containers, keep scoped styles and tokens, and the shell overlay manager orders layers deterministically by observing those roots. Base UI's Drawer has no portal context and keeps portalling into `document.body` (documented limitation). Nothing patches `document.body`, portals or components.

## 5. Tecton as a git dependency

`@tecton/react` is a private, source-only package. The platform installs it from the Tecton repository with pnpm's git subdirectory syntax (`github:rpkapps/tecton-ui-1#<sha>&path:packages/tecton-react`) pinned to a commit. Because it is source, it is compiled by every consumer and is not shared as a built module; its version, CSS protocol and token set are validated separately through the manifest.

## 6. Settings registrations are lifecycle-bound; the shell mounts owners headlessly

A settings group exists while the registering component is mounted. Shells that need a remote's framework-managed groups on a page where the remote is not visible mount it headlessly (`MfeOutlet headless`), which keeps registrations live without breadcrumbs or navigation side effects. The manifest still lists the groups for discovery and search.

## 7. Runtime configuration is generated by a Node entrypoint from `PLATFORM_*` variables

Only variables with the `PLATFORM_` prefix are read; names that look sensitive are refused and reported. The document is organised by `mfeId`, validated before the platform starts, served as `/platform-config.json` or inlined by the SSR shell, and every value carries its source for devtools. Assets are never rebuilt for configuration changes.

## 8. Development servers share nothing

A remote served by `platform dev` registers its shared packages in a private Module Federation scope (`react19:dev:<mfeId>`) and runs on its own copies of React, the router and everything else. In development every dependency comes from the remote's Vite server: pre-bundled modules (`@tanstack/react-router`, React Aria, …) import the optimizer's React directly, so taking React from the shell while those modules keep the remote's copy would split one component tree over two React instances ("Invalid hook call"). Self-contained dev servers also give each remote exactly one refresh runtime (decision 3). Sharing is negotiated by production builds, which the conformance suite covers separately; the manifest keeps the production scopes and `dev.hmr` marks the difference.

## 9. Route-level HMR targets a per-remote router registry

`@tanstack/router-plugin` injects HMR glue into every route file that finds the live route by id on `window.__TSR_ROUTER__` (the one router a page is assumed to have) and copies the module's options onto it when the module evaluates. In a shell that router is the shell's, and every remote's root route is also `__root__`, so a remote's route file would replace the shell's root route with its own component. `@platform/vite` rewrites that lookup (dev server only) to `globalThis.__PLATFORM_TSR_ROUTERS__[mfeId]`, which `@platform/mfe-react` fills with the latest router of the MFE while it is mounted. Route HMR keeps working inside the remote; the shell's router is never touched. The SDK also restores `window.__TSR_ROUTER__` after creating an MFE router, since TanStack Router publishes every client router there.
