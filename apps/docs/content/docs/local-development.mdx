title: Local development
description: Run an MFE through a shell with a manifest override — locally or against a deployed development shell. Full HMR, a real context and real authentication.
---

An MFE is never run on its own: it is mounted by a shell, and the loop that matters is the one
where a shell loads your dev server. That works the same way locally and against a deployed
development shell, which is how you iterate with real authentication and real data.

## The loop

```bash
pnpm dev
```

`platform dev` starts the remote's Vite dev server (port 5173 by default) and serves its
development manifest at `/platform-manifest.json`. Point a shell at it:

```text
https://shell.example.com/asset-tracker?platform.override.asset-tracker=http://localhost:5173/platform-manifest.json
```

Four ways to set that override, all equivalent ([Manifest overrides](/docs/manifest-overrides)):

- the `?platform.override.<mfeId>=<url>` query, which persists into
  `localStorage["platform:manifest-overrides"]`,
- the override control in the shell's [developer tools](/docs/developer-tools), which is the
  one to reach for against a deployed shell,
- `localStorage["platform:manifest-overrides"]` directly,
- `mfes.<mfeId>.manifestUrl` in the shell's [runtime configuration](/docs/runtime-configuration),
  for a shell you deploy yourself.

The dev manifest carries `dev.hmr = true`, `dev.origin`, `dev.refreshPreamble` and
`dev.configHash`. The host imports the preamble before loading, so React Refresh is installed
for that remote's own React instance, then loads the remote through the ordinary loader. Shell
state — route, context, palette — is preserved while your remote updates.

A deployed development shell gives you the shell's real session, so
[`usePlatformFetch`](/docs/authentication) reaches the real backend with a real token. That is
the loop to use for anything that touches data.

In this monorepo, `pnpm dev:conformance` starts the conformance shell on 4110 with every
fixture remote in development mode.

## HMR

- Component edits hot-swap inside the remote's React root; the shell and other remotes do not
  re-render (the E2E suite edits a React 19 route and a React 18 widget and checks that the
  shell counter and the other roots keep their state).
- React 18 and React 19 refresh runtimes are installed per React instance
  (`/@platform/refresh-preamble`) and never mixed.
- Widget instances refresh independently; state held in the shell (slot props, open panels)
  survives.
- The dev manifest is never cached by the host (`dev.hmr = true`).
- Route files hot-update against the remote's **own** router: `@platform/vite` rewrites the
  router plugin's HMR glue from `window.__TSR_ROUTER__` (the shell's router, whose root route
  is also `__root__`) to a per-remote registry the SDK maintains while the MFE is mounted.
- A development server runs on **its own copies** of the shared packages: `@platform/vite`
  registers them in a private share scope (`react19:dev:<mfeId>`), so the remote's pre-bundled
  dependencies, its components and its refresh runtime all use one React instance. Sharing with
  the shell is negotiated by production builds only; the shared-dependency report of a dev
  remote says so (`development server: own copy`).

## Restart diagnostics

Some inputs are read once at startup: `mfe.config.ts` (and its imports), `package.json` (shared
dependency requests, federation configuration) and the generated route tree. When one of them
changes while `platform dev` runs:

1. the dev server re-resolves the configuration; when the config hash differs it sets
   `dev.restartRequired: true` and `dev.restartReason` (`A manifest-affecting input changed
(mfe.config.ts)`, `The generated route tree changed (src/routeTree.gen.ts)`) on the dev
   manifest,
2. `platform dev` logs the `DEV_RESTART_REQUIRED` diagnostic and sends a
   `platform:restart-required` event over the Vite websocket,
3. the shell shows the **restart required** state instead of a stale or partially updated
   remote.

Restart the dev server; the diagnostic clears when the new manifest loads.

## HMR-capable versus production artefacts

Only manifests produced by a development server carry a `dev` block. Production artefacts have
none and are **never** shown as HMR-capable, even when served from `localhost`
(`vite preview`). An artefact sitting next to a dev server of the same `mfeId` is a common
source of "my change does not show" confusion; the developer tools' _Overview_ panel shows an
`HMR` badge only for dev manifests, and says which manifest URL is actually loaded.

## Reaching a failure on purpose

The failures that are hardest to test by hand — a remote that will not load, a 404ing manifest,
an unsatisfiable shared dependency, a denied permission group, a withheld capability — are
switches in the developer tools' _Faults_ panel. They act on the live shell, so what you see is
the real error boundary and the real diagnostic. See [Developer tools](/docs/developer-tools).

## Ports

| App                                                       | Port                                                     |
| --------------------------------------------------------- | -------------------------------------------------------- |
| A remote's dev server (`platform dev`)                    | 5173 by default, `/platform-manifest.json`               |
| Conformance shell (production build / dev)                | 4100 / 4110                                              |
| `asset-tracker`, `legacy-reports`, `widget-a`, `widget-b` | 4201–4204 built (`pnpm e2e`), 4301–4304 in the HMR suite |
| Unavailable-remote fixture                                | 4999 (nothing listens)                                   |
